# 閲覧フロー設計レビュー

## 1. 対象・結論
対象はACV-DD-001 Rev.1.0とし、ACV-BD-001・ACV-DS-001との構造的整合性および現時点で判断可能な性能特性を確認した。ローカル完結・閲覧専用・`Catalog`を深いModuleとする方針は妥当である。一方、以下の必須対応事項は実装前に仕様を整合させる。

## 2. 構造レビュー
| 優先度 | 指摘                                     | 根拠・影響                                                                                                                                                                     | 推奨対応                                                                                                                           |
| :----- | :--------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------- |
| 高     | `Catalog`のProvider取得責務が不整合      | BD-001は`Catalog`がProvider Registryを参照するが、DD-001のシーケンスは`AppShell`がProvider定義を取得する。呼び出し側へProvider知識が漏れ、`Catalog`のDepthとLocalityを損なう。 | `Catalog.discover(rootSelection)`の内部でRegistryを参照する形に統一する。                                                          |
| 高     | `probe`と`listFiles`の順序が図で不明     | DD-001では別操作かつ`listFiles`の事前条件は「Provider検出済み」だが、シーケンス図は1操作に圧縮している。                                                                       | `probe`の結果を受けて`listFiles`を呼ぶ2段階の図に修正する。                                                                        |
| 高     | 部分失敗を状態モデルで表現できない       | DS-001のトップレベル`error`は排他的だが、DD-001はProvider未検出時も他Providerの結果を維持する。                                                                                | `BrowseState`へProvider単位の状態（`ok`、`not_found`、`permission_denied`等）を持たせ、致命的失敗だけをトップレベル`error`にする。 |
| 高     | `readable`だけでは不読理由を表せない     | DS-001の真偽値ではDD-001のサイズ超過・非対応・権限拒否をUIで区別できない。                                                                                                     | `unreadableReason`列挙値を追加する。読取後に判明する失敗はViewStateのError DTOで扱う。                                             |
| 中     | `DirectorySource.clear()`の責務が過大    | 画面内状態の破棄はAppShell/View側の責務であり、DirectorySourceのInterfaceを越える。                                                                                            | 事後条件を「Root Selectionを破棄する」に限定し、画面状態のリセットはAppShellに置く。                                               |
| 中     | `readText`前のガードがシーケンス図にない | DD-001は巨大・非対応ファイルの本文を読まないと定めるが、図では無条件に読取を実行する。                                                                                         | `sizeBytes`、`kind`、`readable`を確認し、不許可なら読取せず状態を返す分岐を追加する。                                              |

## 3. 性能レビュー
| 優先度 | 懸念                               | 想定される影響                                                                                                    | 推奨対応                                                                           |
| :----- | :--------------------------------- | :---------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------- |
| 中     | 一覧生成時のサイズ取得             | File System Access APIでは各ファイルのサイズ取得に`getFile()`が必要であり、ファイル数に比例して走査時間が増える。 | サイズを一覧生成時に必須とするか再検討し、必要なら並列数を制限する。               |
| 中     | `webkitdirectory`の全木列挙        | 選択ルートが広いと、対象外を除外する前に大量のFileListを受け取り、標準Adapterより遅くなり得る。                   | フォールバック時は対象を絞ったフォルダ選択を案内し、件数上限・中断方針を定義する。 |
| 低     | Provider検出の直列実行             | Provider数に応じて初期表示が遅くなる。                                                                            | 独立する`probe`は`Promise.all`等で並列実行することを規定する。                     |
| 低     | 2MiB近傍Markdownの同期レンダリング | parseとサニタイズがメインスレッドを一時的に占有する可能性がある。                                                 | 初期版の許容範囲を明記し、将来のWeb Worker移行条件を定義する。                     |

## 4. 対応優先順位
実装開始前に、構造レビューの高優先度4件をBD-001、DD-001、DS-001で同時に整合させる。中・低優先度は、初期実装の性能計測結果を基に受入基準と実装方針を確定する。
